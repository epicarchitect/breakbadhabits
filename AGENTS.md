# Правила разработки

## Общие принципы

- В любом вопросе опираться на авторитетные источники: исследования, документацию и признанных
  экспертов, а не на «так принято» или случайные мнения.
- Если источники противоречат или недостаточны, проверять первоисточник, контекст и аргументы, а не
  выдавать догадку за факт.
- `AGENTS.md` — только правила, которые меняют поведение агента в этом репозитории. Ключевые правила
  сопровождать кратким обоснованием рядом с тезисом; длинные гайды и исследования сюда не
  переносить, README и код не дублировать.
- `AGENTS.md` должен быть абстрактным и не ссылаться на сущности проекта: имена проектных классов,
  пакетов, путей и API в правилах не упоминать, чтобы правила переносились в другой проект без
  переписывания.

## Аргументы функций

- В собственном коде не использовать default arguments: вызывающая сторона передаёт значения явно,
  чтобы сигнатура не скрывала зависимости и поведение. Это относится к фабрикам, state и API.
- Исключения — стандартные API Compose и модели сериализации, где default задаёт контракт
  библиотеки или совместимость формата; новые такие default не добавлять без необходимости.

## Обновление зависимостей

- Приоритет — самые свежие версии зависимостей, включая alpha, beta, RC и milestone; обновление на
  pre-release приветствуется.
- Перед обновлением проверять известные проблемы версии в официальных источниках: release notes,
  GitHub/GitLab issues, JetBrains YouTrack, AndroidX issue tracker, Stack Overflow и issue tracker
  самой библиотеки. Сборка без ошибок не доказывает отсутствие известных проблем.
- Если у нестабильной версии есть открытые issues, влияющие на проект, не обновляться молча:
  объяснить разработчику риски, привести ссылки на issue и предложить более стабильную альтернативу.
  Обновление на такую версию — решение разработчика, а не автоматический выбор «самой новой».
- После обновления проверять итоговые версии связанных артефактов в runtime-графе, а не только
  успешную сборку: одна зависимость может поднять транзитивную версию соседней библиотеки, и
  приложение упадёт в runtime с `NoSuchFieldError`/`NoSuchMethodError`. Смешанные версии одной
  библиотечной группы недопустимы; откатывать до согласованного диапазона и фиксировать причину.
- Сначала обновлять зависимость на самую новую доступную версию. Если сборка, тесты, lint или запуск
  ломаются, откатываться последовательно: alpha → beta → RC → stable.
- Stable — последний вариант, а не вариант по умолчанию: использовать его только если более новые
  alpha/beta/RC не работают.
- При откате фиксировать конкретную причину и проверенный диапазон версий в описании изменений; не
  оставлять старую версию без объяснения.

## Compose previews

- Каждый новый UI-компонент (`@Composable`, который рисует интерфейс) обязан иметь минимум один
  `@Preview`: иначе состояние нельзя проверить изолированно, без БД и запуска приложения.
- Для существующих компонентов превью добавляются при изменении их внешнего вида.
- Использовать `androidx.compose.ui.tooling.preview.Preview` из
  `org.jetbrains.compose.ui:ui-tooling-preview`.
- Превью-функцию размещать в том же файле, где объявлен компонент, как приватную функцию:
  `private @Composable fun ...Preview()`. Так превью меняется вместе с компонентом и не теряется при
  рефакторинге.
- Не создавать отдельные файлы и пакеты для превью-функций.
- Оборачивать контент в общую тему превью приложения.
- Общие фейковые данные и тему превью можно выносить в helper-файлы, но сам `@Preview` — только
  рядом с компонентом.
- В превью нельзя использовать реальные БД, сеть, платежи и другие глобальные зависимости. Только
  фейковые данные и фейковые состояния.
- Минимум один preview должен показывать обычное состояние компонента. Если у компонента есть важные
  состояния (loading, empty, error, locked/premium, selected, saving), добавить отдельные превью для
  них.
- Для stateful-экрана, который зависит от БД или навигации, нужно вынести stateless-контент и
  превьюить его; сам screen-wrapper может не иметь `@Preview`, если он только связывает зависимости.
- Приватные подкомпоненты могут не иметь отдельного `@Preview`, если они полностью покрыты превью
  родительского компонента. Самостоятельные визуальные блоки превьюить отдельно.
- Компонент считается незавершённым, пока его превью не компилируется и не отображается в Android
  Studio.
- Перед завершением задачи обязательно открыть все новые и изменённые `@Preview` в Android Studio и
  убедиться, что каждое отрисовывается без ошибок, пустого экрана и падений.
- `assemble`/`lint` не заменяют проверку превью: успешная сборка не гарантирует, что preview
  запускается.
- Если превью падает или показывает не тот экран, задача не завершена.

## Адаптивность

- Адаптироваться к окну приложения, а не к устройству: без `isTablet`, `isLandscape`, ориентации,
  модели устройства и сырых размеров. Источник правды — `WindowSizeClass`/Material 3 Adaptive; свои
  брейкпоинты не писать: устройство описывает железо, а доступное место меняют split-screen, складки
  и resize.
- Общего каркаса экрана нет: фон, insets и `imePadding()` задаёт сам экран. Общий `Scaffold`
  дублировал layout и не давал держать бар в списке.
- Body ограничивается по ширине и центрируется через общий компонент адаптивной ширины
  (узкая/широкая); новые ширины добавлять в его набор, не в разметку. Панель в него не заворачивать:
  она должна оставаться full-width по HIG.
- Верхняя панель приложения — обычный элемент layout: первый item `LazyColumn` или первый элемент
  `Column`; full-width, centered title, `titleMedium`, `background` без тон-элевации. Не overlay, не
  `Scaffold.topBar`, не скрывать и не сдвигать при скролле, не резервировать высоту в
  `contentPadding`; status bar inset применяет сама. Не вводить scroll behavior и скрытие бара при
  скролле: польза мала, а поддержка дорогая — своё поведение, компенсации и тесты на жест.
- Модальные экраны с close (paywall) оставляют close доступным; основная кнопка paywall закреплена и
  не уезжает за экран, иначе действие теряется на длинном контенте.
- Multi-pane и складки — только средствами Material 3 Adaptive (`ListDetailSceneStrategy`,
  `SupportingPaneSceneStrategy`, `NavigationSuiteScaffold`); ручная логика складок расходится с
  фактической posture и ломается при resize.
- Ориентацию не блокировать. После поворота, resize/split-screen, fold/unfold, клавиатуры и смены
  `fontScale` top bar, скролл, фокус и выбранные элементы сохраняют корректное состояние.
- Проверять вёрстку при `fontScale` 1.0, 1.3, 1.5 и 2.0: фиксированные высоты не должны обрезать
  текст, а плотные данные (оси графиков, чипы, строки) должны упрощаться или переноситься вместо
  наложения.
- Проверять минимум 360×800, 600×960, 900×1200, 1200×900, 891×412 и book/tabletop posture; для
  adaptive-компонентов — compact/wide previews.

## Edge-to-edge

- Все экраны работают edge-to-edge: системные бары прозрачные, фон и контент рисуются под ними;
  иначе появляются непрозрачные полосы и скачки при показе/скрытии баров. Это касается и экранов без
  скролла.
- На Android использовать `enableEdgeToEdge` с `SystemBarStyle.dark(Color.TRANSPARENT)` и
  `isNavigationBarContrastEnforced = false`; не задавать непрозрачные `statusBarColor`/
  `navigationBarColor`.
- Корневой экран заполняет всё окно. Body не обрезается по нижнему system inset: background и
  карточки проходят под navigation bar.
- Интерактивный контент не должен оказываться под барами: для списков использовать `contentPadding`
  с `WindowInsets.navigationBars`, для нижних кнопок/FAB — `navigationBarsPadding()`. Не оборачивать
  весь экран в safe-area padding.
- `imePadding()` применяется один раз на body экрана; экраны и вложенные блоки не добавляют его
  повторно, viewport меняется в одном месте, а top bar как обычный элемент layout на клавиатуру
  отдельно не реагирует.
- Верхняя панель сама обрабатывает status bar inset; экран не резервирует её высоту и не применяет
  status bar inset повторно.
- На iOS root остаётся `ignoresSafeArea()`, а safe-area insets применяются к интерактивному контенту
  внутри Compose.
- Проверять edge-to-edge с gesture navigation и 3-button navigation, с cutout, в portrait/landscape
  и на экранах с фиксированной нижней кнопкой и без неё.

## Баги и замечания

- Если найден баг или разработчик оставил замечание, исправлять не только симптом, но и причину:
  после фикса обновить `AGENTS.md`, если нужно не допустить повторения этого класса ошибок.
- Если дефект не удаётся исправить за несколько итераций, остановиться и пересмотреть архитектуру
  решения в целом: найти дублирующиеся источники состояния и обходные компенсации, свести поведение
  к одному источнику правды. Не продолжать точечные патчи поверх неверной модели.
- Если повторение можно поймать тестом, добавить регрессионный тест (unit, UI или preview-проверку).
  Если тест объективно невозможен, зафиксировать в правилах ручной сценарий проверки и причину,
  почему автоматизация не подходит.
- Не закрывать замечание одним патчем без проверки, что исправление не ломает соседние состояния:
  поворот, resize, клавиатуру, скролл и навигацию.
- В `RemoteViews` на каждой привязке явно задавать видимость и значения всех условных view:
  переиспользуемые view сохраняют состояние предыдущего элемента, и пустой элемент начинает
  показывать чужие данные. Проверять список, где пустой элемент стоит между заполненными.

## Проверка перед завершением задачи

- Запускать сборку и lint затронутых Android-вариантов.
- iOS-сборку и iOS-тесты не запускать во время разработки. Проверять их только по явному запросу;
  изменения в общем или iOS-коде сами по себе не запускают iOS-проверку.

## Архитектура: The Last Arch (ластарч)

The Last Arch — не фиксированная слоистая схема, а принципы выбора архитектуры.

- Сущность — минимальная единица, за существование которой мы платим когнитивную стоимость:
  интерфейс, класс, функция, модуль.
- Бизнес-логика — весь код, кроме утилитарного (библиотеки, корутины, Room, навигация,
  дизайн-система). UI-логика — тоже бизнес-логика: не выносить её в отдельный слой только ради
  названия.
- Чем меньше сущностей и связей между ними, тем лучше: прямые зависимости и вызовы предпочтительнее
  цепочек посредников.
- Использовать базу данных/DAO напрямую. Не создавать репозитории, интеракторы, use case-классы,
  domain-слой и лишние мапперы.
- Сценарии реализуются функциями рядом с использованием в presentation/фиче, а не отдельными
  domain-классами.
- Можно напрямую зависеть от DAO/БД другой фичи. Не создавать domain-прокси ради «сырых данных» и не
  искажать данные (`null` → `orEmpty`), если это меняет смысл.
- Не добавлять DI-фреймворк: зависимости передаются напрямую или через существующие точки входа.
- Задача решается из требований, а не из «так принято». Clean Architecture, обязательные слои и
  единая ViewModel нельзя добавлять тк 99,9% задач можно решить без этого.
- Абстракция и инверсия зависимостей — точечно и с аргументом. Количество зависимостей — повод
  подумать, а не требование абстрагироваться. Интерфейсы «на будущее» не создавать.
- Не дублировать модели и не мапить data → UI, если UI-модель повторяет data. Логика должна
  находиться рядом с использованием.
- Не оптимизировать преждевременно: сначала доказать проблему, потом усложнять код. Не копировать
  data-модели в UI-модели «ради стабильности Compose» без измерений: это дублирование и лишние
  мапперы.
- Сущность должна окупаться: полезная нагрузка больше двух, переиспользование, частая изменяемость
  или много зависимых. Прокси с полезной нагрузкой 1 убыточен.
- Минимизация не означает свалку в один файл: удобство разработки тоже важно, но усложнение должно
  быть точечным и аргументированным.
- Постоянно задаваться вопросом: можно ли проще?
- Не проверять `lateinit`-зависимости на `null`, по контракту они всегда инициализированы.

### Полезная нагрузка

Полезная нагрузка — приблизительное количество самостоятельных решений внутри сущности: условий,
ветвлений, вычислений, преобразований, проверок и побочных эффектов. Это не точная метрика и не
правило для автоматической проверки, а способ ответить на вопрос: «делает ли сущность что-то
полезное, кроме проксирования?».

- Вызов другой сущности сам по себе не добавляет полезную нагрузку.
- `fun getItems() = repository.getItems()` — нагрузка 0: сущность только проксирует вызов.
- `fun isEnabled() = features[Toggle]` — нагрузка 1.
- `fun isEnabled() = features[Toggle] || isAbTestEnabled()` — нагрузка 2.
- Если нагрузка равна 1 и сущность только передаёт вызов дальше — она убыточна.
- Порог «больше двух» приблизительный: он нужен, чтобы остановиться и подумать, а не чтобы
  механически считать.

Типичные нарушения: domain-слой с проксирующими use case и репозиториями; копирование моделей между
слоями и мапперы; оптимизации без измерений; интерфейсы «на будущее».

## Дизайн

- Если задача сформулирована как проработка дизайна, редизайн или поиск визуального решения, сначала
  провести ресерч: UX-исследования и паттерны, Pinterest, Dribbble, референсы конкурентов.
- По результатам ресерча предложить 5 различимых концептов с краткими плюсами/минусами: так решение
  выбирается из альтернатив, а не принимается первый вариант.
- Концепты обязательно оформлять в виде HTML-макетов, которые можно открыть в браузере и сравнить:
  сравнение в реальном рендере надёжнее описания.
- Не реализовывать дизайн до выбора концепта пользователем.
- Мелкие правки существующего UI без изменения концепции можно делать без пяти концептов.

## UI-система

- Радиусы, типографика и поверхности задаются через `MaterialTheme`; отступы и высоты контролов
  задаются локально в месте использования. Не хардкодить размеры шрифта и цвета поверхностей.
- Одинаковые по смыслу блоки используют общий контейнер или строку и общий внутренний padding;
  отличие оформления передаётся параметром компонента, а не копией. Это удерживает карточки и списки
  в одном ритме.
- Основные и вторичные действия собираются из общих контролов с одной высотой и формой; не
  дублировать кнопку вручную через `Surface`/`Box`. Иначе меняются touch target, типографика и
  состояния.
- Новый компонент в общий кит добавляется только при повторяющемся паттерне; одноразовый блок
  остаётся рядом с экраном, чтобы не плодить прокси.
- Сначала использовать стандартный Material-компонент и настраивать его через `MaterialTheme`/
  `Defaults` и локальные параметры. Обёртку создавать только при повторяемом поведении или
  собственной логике; UI-кит не должен расти из-за простых контейнеров, иконок и строк.
- Бесполезные обёртки над Compose-компонентами не создавать: если обёртка только подставляет
  контейнер, padding или shape без собственной логики, использовать исходный composable в месте
  вызова.
